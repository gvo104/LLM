# Лабораторная работа №1. Пайплайны LangChain и LLM

## Цель работы

Целью было собрать прототип интерфейса к каталогу товаров, в котором запрос
пользователя на русском языке превращается в безопасный поиск по SQLite. В
работе важно разделить обязанности: модель понимает язык и возвращает
параметры, а Python-код проверяет их и обращается к базе.

## Как устроено решение

Основной поток данных выглядит так:

```text
Запрос пользователя
  → ChatPromptTemplate → ChatOpenAI → PydanticOutputParser
  → ProductQuery → параметризованный SQLite-запрос → товары
```

`ProductQuery` содержит `category`, `max_price` и `sort_by`. Эта модель
используется во всех частях работы: для structured output, поиска, tool calling
и хранения состояния диалога. Модель не создаёт SQL. Она возвращает только
параметры, а SQL-шаблон формирует `ProductRepository` из разрешённых полей и
связывает с отдельными значениями параметров.

## Базовая цепочка

В первой части system-сообщение задаёт роль классификатора, а human-сообщение
передаёт переменную `query`. Непосредственный вызов модели вернул `AIMessage`
с содержимым `laptop`; та же цепочка с `StrOutputParser` вернула текстовый
результат `laptop`. Batch из трёх реплик дал категории `laptop`, `smartphone`
и `other`.

Это показывает разницу между сообщением модели и результатом простого
текстового parser. Фактический вывод сохранён в `reports/results/part1.json`.

## Structured Output и режим thinking

Для structured output используется `PydanticOutputParser`. Его инструкции
формата подставляются в system prompt, поэтому модель должна вернуть полный
`ProductQuery`. Семь проверочных и неоднозначных запросов успешно прошли
валидацию и сериализацию в JSON.

На двух неоднозначных запросах сравнивались обычный режим и thinking с effort
`low`:

| Запрос | Режим | Время, c | Input / output tokens | Интерпретация |
| --- | --- | ---: | ---: | --- |
| «Покажи что-нибудь недорогое для учёбы» | off | 0.359 | 402 / 35 | `other`, без лимита, `price_asc` |
| тот же запрос | low | 3.094 | 426 / 398 | `laptop`, без лимита, `price_asc` |
| «Хочу устройство до шестидесяти тысяч, сначала лучшие» | off | 0.402 | 406 / 40 | `other`, 60000, `price_desc` |
| тот же запрос | low | 1.582 | 430 / 201 | `other`, 60000, `price_desc` |

Thinking заметно увеличил время и число выходных токенов. В первом примере он
также изменил категорию, поэтому reasoning нельзя считать гарантированным
улучшением качества. Во всех четырёх случаях parser смог разобрать поле
`content`; рассуждение не передаётся в SQLite как отдельный текст.

Подробнее: `reports/results/part2.json`. (хотелось посмотреть как измениться если прокинуть thinking, по итогу не однозначно по качеству, но дольше по генерации)

## Поиск в SQLite и tool calling

В базе есть 15 товаров: не менее четырёх ноутбуков, смартфонов и планшетов.
Поиск поддерживает фильтр по категории и верхней цене, а также оба направления
сортировки. Все пользовательские значения передаются в SQLite параметрами.
Если категория распознана как `other`, поиск не выполняется и пользователь
получает понятное сообщение.

Сквозной pipeline правильно обработал 10 из 10 контрольных запросов. CLI для
каждого из них сохраняет исходную реплику, распарсенный `ProductQuery`,
SQL-шаблон, параметры SQL и список товаров. В сравнении без базы модель
корректно отказалась выдавать выдуманный локальный каталог.

В варианте с инструментом модель вызвала `search_products` для всех пяти
проверок. Результаты были следующими: 2 ноутбука до 70 000 ₽, 5 дорогих
смартфонов, 5 планшетов, 1 ноутбук до 50 000 ₽ и сообщение о неподдерживаемой
категории для холодильников. Аргументы tool call повторно проверяются через
`ProductQuery` перед доступом к SQLite, а найденные товары обратно в модель не
отправляются.

Фактические данные: `reports/results/part3.json`.

## Retry и журнал

Были подготовлены три невалидных ответа модели: невалидный JSON, неизвестная
категория и отрицательная цена. Все они завершаются ошибкой parser. Retry
охватывает только участок `LLM → parser`; SQLite находится после него и не
повторяется.

| Сценарий | LLM-вызовы | SQLite-вызовы | Результат |
| --- | ---: | ---: | --- |
| Невалидный JSON без retry | 1 | 0 | `OutputParserException` |
| Ошибка, затем корректный JSON | 2 | 1 | Поиск выполнен |
| Три невалидных ответа | 3 | 0 | Понятное сообщение об исчерпании попыток |
| Сетевая ошибка | 1 | 0 | Повтора нет |
| Категория `other` | 1 | 0 | Поиск пропущен |

Журнал содержит идентификатор запроса, этап и номер попытки. Типичный фрагмент
выглядит так:

```text
stage=llm         Начало попытки 1.
stage=parse_error OutputParserException
stage=llm         Начало попытки 2.
stage=parse       Параметры успешно проверены.
stage=sqlite      Найдено товаров: 2.
```

В журнал не записываются токен, `.env` и HTTP-заголовки. Полные offline
артефакты находятся в `reports/results/parser_errors.json` и
`reports/results/retry_demo.json`.

## Уточняющие запросы

Реализованы два способа передать контекст следующей реплике:

- compact state хранит только последний валидный `ProductQuery` в Python;
- full history передаёт все пары Human/AI сообщений, где ответ AI — JSON
  последнего валидного `ProductQuery`.

На двух диалогах по три реплики compact state правильно обработал все 6 ходов.
Full history справился с 5 из 6 и использовал больше входных токенов:

| Режим | Корректные ходы | Входные токены |
| --- | ---: | ---: |
| Compact state | 6 / 6 | 2681 |
| Full history | 5 / 6 | 2801 |

На фразе «А что есть среди смартфонов?» history сохранил сортировку, но потерял
предыдущий лимит 80 000 ₽. В результате он вернул 5 смартфонов вместо 3.
Compact state сохранил все параметры. Этот случай показывает, что более длинная
история не обязательно точнее и расходует больше контекста.

Результаты: `reports/results/dialogues.json`.

## Ответы на контрольные вопросы

1. Пайплайн выполняет заранее определённые шаги, а агент сам выбирает действия
   и инструменты во время работы.
2. LCEL соединяет runnable-компоненты оператором `|`; `StrOutputParser`
   извлекает текст из ответа модели.
3. System-сообщение задаёт роль и правила, human-сообщение содержит конкретную
   пользовательскую реплику.
4. Structured Output — это ответ в заданной схеме; произвольный текст не
   гарантирует поля и типы.
5. `BaseModel` описывает схему, `Field` — ограничения и описание, `Literal` —
   допустимые значения.
6. Без SQLite модель не знает реальный состав и цены локального каталога.
7. В prompt-варианте приложение парсит текст модели; при tool calling сервер
   разбирает вызов, но приложение всё равно валидирует аргументы и выполняет
   действие самостоятельно.
8. Валидация не допускает ошибочные параметры к классическому ПО. SQL,
   сгенерированный моделью, нельзя выполнять без ограничений и параметров.
9. Retry нужен для ошибок формата. Повторная генерация повторно вызывает
   модель, тогда как исправление могло бы использовать текст предыдущей ошибки.
10. Состояние диалога хранится в Python-объекте; модели передаются либо
    последние параметры, либо полная история текущего диалога.

## Вывод

Работа демонстрирует полный управляемый pipeline: parameterized prompts,
structured output, SQLite, tool calling, retry, журнал и диалоговое состояние.
Offline-тесты и live-артефакты подтверждают работу всех частей. Главный вывод:
для этой задачи компактное валидированное состояние оказалось и дешевле по
токенам, и надёжнее передачи полной истории.
